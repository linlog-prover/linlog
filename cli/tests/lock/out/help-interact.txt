Prove a sequent step by step, reading commands from standard input

The session starts with the whole sequent as the one open goal; the sequent is an argument or `--file`, since standard input carries the commands. Commands, one per line, their words split as a shell splits them (quotes keep a name with blanks one word): `goals` lists the open goals with the positions of their formulas; `rules G P` lists the rules that act on formula P of goal G; `apply G P RULE [P…]` applies a rule, the further positions being the formulas that go to the left premise of a ⊗ or Mix; `undo` retracts the last step; `close [G]` lets the search close goal G, or every open goal; `show [--FORMAT] [FILE]` draws the derivation so far, open goals included, as text, or --latex, --typst, --svg, --png or --pdf; `proof [--FORMAT] [FILE]` checks the finished proof and prints or writes it, as JSON for `check` with a FILE and no format, or --rocq for a certificate; `save FILE` and `load FILE` keep and resume the session as JSON (`load` takes a session of the same sequent and mode); `help`; `quit`. A RULE is a rule's usual name or its ASCII spelling: ax, 1, bot, top, *, par, &, +1, +2, ?d, ?c, ?w, !, mix, wk (affine weakening), and in intuitionistic mode the two-sided names (-oL, -oR, *L, *R, &L1, &L2, &R, +L, +R1, +R2, 1L, 1R, 0L, topR, !L, !R, !c, !w); `rules` prints the names it applies. The exit status is 0 when the session ends with a finished proof that checks and 1 otherwise; a command's error is printed as `error: …` on standard output and the session goes on; 2 when the session cannot start or read its input.

Usage: linlog interact [OPTIONS] [SEQUENT]

Arguments:
  [SEQUENT]
          The sequent, such as "A, A -o B |- B"; read from --file when absent, or from standard input by every command but `interact`

Options:
  -f, --file <PATH>
          Read the sequent from this file, or `-` for standard input (but in `interact`, whose commands come from there)
          
          The file's kind is its extension's unless --input-format says otherwise: `.p` an LLTP problem (under --logic, where a command takes it, a TPTP problem of ordinary logic), `.spec` a coverability problem, `.json` a JSON sequent, anything else the text syntax, which may span lines. `prove` takes the flag more than once, and a directory, as a batch.

      --input-format <FORMAT>
          How to read the input, rather than by the file's extension
          
          `lines`, `jsonl` and `problems` hold many sequents, which `prove` decides as a batch.

          Possible values:
          - auto:     By the file's extension: `.p` lltp (tptp under --logic, where a command takes it), `.spec` spec, `.json` json, else text
          - text:     One sequent in the text syntax, which may span lines
          - json:     One sequent in JSON, as `seq json` writes it
          - lltp:     A problem of the LLTP library: its axioms ⊢ its conjecture; the file does not say whether it is intuitionistic, the flags do
          - spec:     A coverability problem in the .spec format of the Mist tool: its rules under !, its initial marking ⊢ its target, a question of affine mode, in which it is decided without --affine
          - lines:    One sequent per line in the text syntax, as `NAME: SEQUENT` or `SEQUENT`; blank lines and everything from `#` on are skipped
          - jsonl:    One JSON value per line: a sequent as `seq json` writes it, or {"name": …, "mode": …, "sequent": …} with the sequent in JSON or as text and the mode named as in `problems`; blank lines are skipped
          - tptp:     A problem of ordinary propositional logic in TPTP syntax, as the ILTP library writes them: its axioms ⊢ its conjecture (with --logic, where a `.p` file is one)
          - problems: The benchmark harness's problem files: `NAME; MODE; EXPECTED; COPIES; SEQUENT` per line, MODE one of classical, mix, affine, intuitionistic or intuitionistic-affine; EXPECTED and COPIES are not read
          
          [default: auto]

      --occurrence-limit <N>
          The most subformula occurrences the sequent may have, or `none` (limits.occurrences)
          
          A sequent in JSON can share subformulas, so a small file may stand for a sequent of any size; one beyond the limit is refused before it is unfolded. Occurrences cost some 25 bytes each before any search, and no limit lets through more than about four billion. A text nested deeper than the limit (more `(` or `~` open at once) is refused the same way.
          
          [default: 50000000]

      --state <PATH>
          Resume a session saved with `save` instead of starting from a sequent; the mode is the file's, so the mode flags are refused

  -i, --intuitionistic
          Intuitionistic linear logic: one formula on the right of ⊢, pars only as implications, and two-sided derivations

  -a, --affine
          Affine logic: a hypothesis may go unused (weakening)

      --mix
          Allow the Mix rule, which proves ⊢ Γ, Δ from ⊢ Γ and ⊢ Δ

      --bias <BIAS>
          How the focused engines pick the positive literal of every atom (search.bias)
          
          No choice changes what is provable. `rarer` mostly chains backward from the goal, `factors` forward from the hypotheses, which on Horn clauses under `!`, such as a Petri net, is often much faster but takes one copy per step on a single branch. `auto` takes `rarer` in affine mode, `factors` in linear mode without exponentials, and in linear mode with exponentials runs both searches and answers with the first that decides: alternating on one core, side by side on several.

          Possible values:
          - auto:    `rarer` in affine mode, `factors` in linear mode without exponentials, and in linear mode with exponentials both, each in a search of its own
          - rarer:   The literal with fewer occurrences is positive
          - factors: The literal that is more often a direct factor of a tensor is positive, so that more splits are forced
          
          [default: auto]

      --copies <N>
          How often `?` formulas may be copied on one branch of the proof, or `none` for no bound (search.copies)
          
          The search tries the bounds 0, 1, … in turn. By default it goes on to the next bound until it decides or the time limit passes, and an unknown verdict says which bound it reached. With a bound, a sequent with exponentials that has no proof within it is unknown (exit status 3) unless a smaller bound already exhausted the search space, in which case it is unprovable. Sequents without exponentials are not affected.
          
          [default: none]

      --forward-copies <N>
          How often `?` formulas may be copied on one branch of the forward search that `--bias auto` runs (search.forward_copies)
          
          It applies to a Horn program: clauses such as `!(a * b -o c * d)`, a marking and a goal of atoms, as a Petri net is. There a copy is one step of a chain, and a chain of n steps needs n of them. The forward search never runs within less than `--copies`; on any other sequent, and under Mix, it runs within `--copies`. Without a bound from `--copies` it has no effect: both searches deepen while the time limit lasts.
          
          [default: 30]

      --timeout <DURATION>
          Give up after this long, such as 500ms, 10s, 2m or 1h, or `none` for no limit (clock.time_limit_ms)
          
          The verdict is then unknown (exit status 3). The time counts from the start of the command, so it covers reading and parsing the sequent as well as the search: a sequent that is not read in time is given up on like one that is not decided. Without the limit, the search runs until it decides or is interrupted with Ctrl-C, which with exponentials and no `--copies` bound can be forever. In a session it is each `close`'s limit.
          
          [default: 2s]

      --memo-limit <N>
          The most decided sequents the search remembers at once (search.memo_limit)
          
          When the memo is full it is emptied, which costs time but not correctness. Zero switches the memo off. `--memory-limit` bounds the memo in bytes; this is the finer knob beside it.
          
          [default: 1048576]

      --memory-limit <SIZE>
          The most memory the search may hold: a number of bytes with a unit such as 512MiB or 4GiB, or `none` for no limit (limits.memory_bytes)
          
          Counted is what grows with the search: what it remembers, the proofs it keeps and what every level of its recursion takes; not the sequent itself. A memo that no longer fits is emptied first, as at `--memo-limit`; when that is not enough the verdict is unknown (exit status 3). The check of the proof and the derivation built from it are under the same limit: a derivation estimated above it is left out even with `--derivation-limit none`. By default one thread and, after `--pool-after`, a pool beside it search at once, both together within the limit. A png or pdf render is estimated before it starts, its time counted as the memory the renderer fills in it, and left out above the limit (the default is a few seconds of rendering).
          
          [default: 1GiB]

      --recursion-limit <N>
          The deepest nesting of rules on one branch before the search gives up (limits.recursion_depth)
          
          Raise it for sequents with thousands of connectives; the search runs on a thread whose stack grows with the limit.
          
          [default: 2048]

      --work-limit <N>
          The most units of work the search may do, or `none` (limits.work)
          
          A unit is what each engine counts at its polls (a stable sequent or a split for the focused engine, a literal or a failed test for the net engine, a pair for the additive one, a marking for the Horn engine), so a limit gives the same verdict on every machine where a time limit does not; past it the verdict is unknown (exit status 3). `--stats` prints the units a search did.
          
          [default: none]

  -j, --jobs <N>
          How many threads the search may use (search.jobs)
          
          By default one thread searches first, for the time `--pool-after` gives, and then the machine's other threads join it: a small sequent is decided at once and always the same way, a hard one gets every core. A number given here is used from the start, unless `--pool-after` is given too; a number above the machine's parallelism is taken as that, with a note on standard error. More than one runs the focused engine and the net engine on that many threads; the proof found may then differ from run to run, the verdict never does.

      --pool-after <DURATION>
          How long one thread searches before the other threads join it, such as 100ms; 0 starts them at once (clock.pool_after_ms)
          
          The default is 100ms when `--jobs` is not given, and 0 when it is. The single thread goes on searching beside a pool of the other threads, which starts the search afresh, and the first to decide answers; both together hold at most `--memory-limit`. Below three threads there is no single thread: two search on a pool from the start. The additive and the Horn engine run on one thread and get no pool.

      --deterministic
          Run the sequential engines, whose proof is a function of the input
          
          The same as `--jobs 1 --schedule turns`, and takes precedence over `--jobs`, `--pool-after` and `--schedule`.

      --test-period <N>
          How often the net engine runs its exact test of correctness: after this many links, or `auto` (search.test_period)
          
          `auto` tests after every link on a small structure and every few links on a large one. The verdict never depends on it.
          
          [default: auto]

      --schedule <SCHEDULE>
          How the two searches of `--bias auto` share one thread (search.schedule)

          Possible values:
          - auto:  In slices on two threads
          - turns: In turns on the calling thread, each turn from the search's start: the same answer and the same counts on every machine
          
          [default: auto]

      --derivation-limit <SIZE>
          The largest derivation `close` grafts, by its estimated size; see `prove --derivation-limit` (limits.derivation_bytes)
          
          [default: 64MiB]

      --style <KEY=VALUE>
          Set an option of an output format, such as `labels=subscript`, `latex.open=bare` or `svg.font.family=monospace` (repeatable) (styles.FORMAT.KEY)
          
          KEY is a field of the format's options, dotted into nested ones, as `--style-file` holds them; without a prefix `text.`, `latex.`, `typst.`, `svg.`, `png.`, `pdf.` or `rocq.` it names the format `--format` gives. VALUE is JSON, or else a string: `gap=5`, `ids=true`, `open={"mark":"?"}`, `labels.table.⊸L=⊸_L`. The fields: text: labels, open, bar, gap; latex: form, labels, open, align, ebproof, preamble; typst: form, labels, open, import, page, layout (auto, curryst or linlog: curryst for a tree up to nine inferences high, linlog's own code above), premise_gap, label_gap, band, stroke (lengths for linlog's own layout: a number and pt, mm, cm, in or em); svg: font (family, advances), labels, open, ids, description, font_size, label_size, line_height, premise_gap, literal_gap, label_gap, margin, stroke_width, link_height, link_cap, node_radius, text, line, par, link, highlight, background; png: scale, pixels; pdf: embed_text, compatible, accessible, title, language, date; rocq: form, lemma, prelude (where the command writes Rocq). `null` lifts a bound (`pixels=null`). Labels are upright, subscript, off or {"table":{RULE:LABEL}}; an open goal is dots, bare, dashed or {"mark":TEXT}

      --style-file <PATH>
          Read the options of the output formats from a JSON file: an object with a key per format (text, latex, typst, svg, png, pdf, and rocq where the command writes Rocq), each holding the fields `--style` names; a field left out keeps its default (styles)

      --lemma <NAME>
          The name of the lemma of a Rocq certificate (styles.rocq.lemma)

      --prelude <TEXT>
          The lines a standalone Rocq file starts with, before the lemma, in place of the certificate's own import (styles.rocq.prelude)

      --settings <PATH>
          Read the settings from a JSON file, before the flags, which override it: an object with any of the keys `clock`, `limits`, `search`, `view`, `styles`, `batch` and `ordinary`, each an object of the fields the flags name in parentheses (`{"search": {"copies": 3}, "limits": {"memory_bytes": null}}`); a field left out keeps the command's default, and a misspelt one is an error; `ordinary` applies under --logic, which names the logic

  -h, --help
          Print help (see a summary with '-h')

Sequent syntax: `A, B |- C, D` (or `⊢`), either side may be empty.
  tensor  A * B, A ⊗ B        par   A | B, A par B, A ⅋ B
  with    A & B               plus  A + B, A ⊕ B
  linear implication  A -o B, A ⊸ B
  negation  ~A, A^            exponentials  !A, ?A
  units  1, bot, ⊥, top, ⊤, 0
Binding, tightest first: A^, then ~ ! ?, then *, |, &, +, and last -o, which
groups to the right.
